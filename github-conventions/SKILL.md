# GitHub Conventions

Three conventions bind every skill in this collection that publishes text on GitHub or creates a
branch. They are the owner's rules, not a project's, so they apply to every repository and are not
overridable by a repository that says nothing about them. A repository that states its own branch
scheme wins on branch naming only; the signature is never optional.

## 1. Sign every published text

Every text an agent publishes on GitHub ends with one signature line, preceded by a blank line:

```
🤖 AI-generated by <mark> <Agent> <Model> (<Reasoning>)
```

| Vendor    | Agent names                     | Mark | Codepoint | Name                                       |
| --------- | ------------------------------- | ---- | --------- | ------------------------------------------ |
| Anthropic | Claude                          | `❋`  | U+274B    | Heavy Eight Teardrop-Spoked Propeller Asterisk |
| Google    | Gemini, Antigravity             | `✦`  | U+2726    | Black Four Pointed Star                    |
| OpenAI    | ChatGPT, Codex                  | `֎`  | U+058E    | Left-Facing Armenian Eternity Sign         |

```
🤖 AI-generated by ❋ Claude Sonnet 5 (High)
🤖 AI-generated by ✦ Gemini Pro 3.1 (Low)
🤖 AI-generated by ֎ Codex GPT 5.6 Sol (Medium)
```

Name the model actually running, not the family, and the reasoning or effort level the session is
actually running at. When the level genuinely cannot be determined, drop the parenthesis rather
than guessing one; never drop the mark or the model.

**Signed:** issue bodies, issue comments, pull request bodies, pull request comments, review
bodies, inline review comments, review thread replies, and issue or PR titles' accompanying
bodies. Every one of them, including a one-line comment.

**Not signed:** commit messages, release notes, tags, files written into the repository, labels,
and anything shown only in chat. Those belong to the project, not to the agent.

When a body is edited rather than replaced, the signature is rewritten to the agent performing the
edit, and stays a single line. Two stacked signatures mean the previous one was not replaced.

## 2. Name the branch for the agent, not the worktree

```
<type>/<agent>/issue-<NNN>/<short-description>
```

```
feature/claude/issue-024/add-button
fix/codex/issue-107/expired-session-check
```

- `type`: `feature`, `hotfix`, `fix`, `chore`, `docs`, `refactor`, `test`.
- `agent`: exactly one of `claude`, `codex`, `gemini`. Nothing else is a valid value. Map the
  running agent through the table above: Claude to `claude`, Gemini and Antigravity to `gemini`,
  ChatGPT and Codex to `codex`.
- `issue-<NNN>`: the issue number, zero-padded to three digits.
- `<short-description>`: two to four kebab-case words describing the change.

The worktree's directory name, a tool-generated branch name, and a session identifier are none of
them a reason to deviate. If a branch already exists under a generated name, rename it
(`git branch -m`) before pushing, or create the correctly named branch and push that one. "It is
what the worktree is called" is not an exemption.

## 3. Publish the verdict, even when the API refuses it

GitHub rejects a formal `APPROVE` on a pull request the same account authored, and can reject a
formal review event for other reasons. That is a rejection of the review *event*, never a reason
to publish nothing.

When the formal review cannot be submitted, post the same content as a pull request comment whose
first line is the verdict:

| Verdict           | First line             |
| ----------------- | ---------------------- |
| Approve           | `Approved ✅`          |
| Request changes   | `Requested Changes 🔄` |
| Comment only      | `Commented 💬`         |

The body below it is the review body unchanged, with each finding naming its file and line, since
a plain comment cannot anchor to the diff. The signature closes it as normal.

Then report accurately: the findings were published as a comment, the formal review event was
refused and why, and which separate reviewer action is still required. Never claim a formal
approval GitHub rejected, and never let the refusal end with nothing published at all.
